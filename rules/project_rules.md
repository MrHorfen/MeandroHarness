# 项目规则

## 核心业务逻辑（强制执行）

### PDF独立性原则（冷启动）

**核心原则：每一份PDF都是独立的业务任务，必须冷启动处理。**

**具体规则：**
1. **不跨PDF共享状态**：处理新PDF时，不得复用之前PDF的任何上下文信息（如页数、乐器类型、声部信息等）
2. **自动检测PDF属性**：每次接收新PDF，必须重新检测总页数、乐器类型、声部信息等
3. **不硬编码页数**：禁止在代码中硬编码 `page_range=[0,1,2]` 等固定页数，必须自动检测PDF总页数
4. **独立输出文件**：每个PDF的输出文件必须独立命名，不得覆盖或混淆

**错误示例：**
```python
# ❌ 错误：硬编码页数，把之前PDF的信息套用到新PDF
page_range=[0, 1, 2]  # 之前PDF是3页，但新PDF可能是5页
```

**正确示例：**
```python
# ✅ 正确：自动检测PDF总页数
doc = fitz.open(pdf_path)
total_pages = len(doc)  # 自动检测
normalized_paths = normalizer.normalize_pdf(pdf_path, output_dir)  # 处理所有页
```

**业务场景说明：**
- 用户可能连续处理多个不同PDF（如3页的舒曼原版、5页的音协考级版）
- 每个PDF的页数、乐器类型、声部信息都可能不同
- 系统必须在每次处理时重新检测，不得假设或复用之前的信息

### 第二步：PDF 标准化预处理（强制执行）

**核心原则：** 每接收到一份PDF，都必须先进行标准化预处理，确保达到Audiveris技术边界标准后，再进行转谱。

#### 2.0 Audiveris 技术边界（知识库）

**图像输入要求：**
| 参数 | 标准要求 | 说明 |
|------|----------|------|
| **DPI范围** | 200-500 DPI | 推荐300 DPI（A4标准），小符号用400 DPI |
| **谱线间距** | ~20像素 | 两条谱线之间的垂直距离（关键指标） |
| **图像格式** | **灰度图像** | 禁止使用RGB彩色或纯黑白二值图像 |
| **最大像素数** | **20,000,000** | 硬性限制（2000万像素），超过会识别失败 |
| **二值化** | **禁止预先二值化** | Audiveris有自适应二值化算法，预二值化会导致失败 |

**处理能力边界：**
- ✅ **能自动检测**：图像旋转/歪斜
- ❌ **不尝试图形校正**：保持扭曲谱线原样，作为局部参考
- ⚠️ **应关闭**：扫描软件的后处理（Line Art、Text、Dithering、Halftone）

**官方推荐的图像增强方法：**
1. **亮度/对比度调整**：使用颜色曲线，保持暗部黑色
2. **高斯模糊**：半径1.5-2.0，去除噪声
3. **非锐化掩模**：标准差约1.0，重新锐化
4. **低分辨率放大**：使用waifu2x等超分辨率工具

**识别方法：**
- 混合方法：传统计算机视觉 + 神经网络字形分类器（5.x版本）
- 不需要GPU
- 基于手工规则的布局分析和音乐解释

#### 2.1 PDF 标准化预处理流程

**目标：** 将任意质量的PDF转换为符合Audiveris技术边界的标准输入

**标准化步骤：**

1. **渲染PDF为灰度图像**
   - 使用PyMuPDF渲染，目标DPI=300
   - 输出格式：灰度PNG（不是RGB）

2. **尺寸标准化**
   - 计算总像素数（宽×高）
   - 如果超过2000万像素，等比缩小至限制内
   - 确保谱线间距接近20像素

3. **歪斜检测与校正**
   - 检测歪斜角度（-5°到+5°范围）
   - 自动校正歪斜

4. **图像增强（温和）**
   - 对比度增强（系数1.2）
   - 轻微高斯模糊去噪（半径0.5-1.0）
   - 非锐化掩模重新锐化

5. **质量验证**
   - 检查像素数是否<2000万
   - 检查是否为灰度图像
   - 检查谱线间距是否接近20像素

**执行原则：**
- 所有PDF必须先经过标准化预处理
- 标准化后的图像保存到 `temp/normalized_scores/` 目录
- 验证通过后才送入Audiveris识别

#### 2.2 固定范围水平切割方案（推荐）

适用于钢琴+合唱混合谱，需提取钢琴部分、去除人声声部的场景。

**核心原理：**
- 基于Y坐标（垂直位置）进行水平切割
- 根据页面中"Pno."标识位置确定钢琴区域范围
- 使用PyMuPDF提取指定Y范围的页面内容

**实施步骤：**

1. **分析页面布局**
   - 扫描页面文本块，定位"Pno."和声部标识（如"S.", "A.", "T.1", "B."等）
   - 记录各标识的Y坐标
   - 第一页布局通常与其他页不同，需特殊处理

2. **确定切割范围**
   - 钢琴区域通常在Y坐标的固定区间内
   - 示例范围（需根据实际页面调整）：
     ```python
     # 第一页特殊处理（布局不同）
     if page_num == 0:
         piano_ranges = [
             (50, 280),    # 开头钢琴区域
             (300, 450),   # 中间钢琴区域
             (700, 850),   # 下方钢琴区域
         ]
     else:
         piano_ranges = [
             (200, 350),   # 上方钢琴区域
             (650, 800),   # 下方钢琴区域
         ]
     ```

3. **执行切割**
   - 每个钢琴区域创建独立页面，避免重叠
   - 使用白色矩形遮盖非钢琴区域内容
   - 保存为新的PDF文件

4. **验证结果**
   - 检查输出PDF是否完整包含钢琴部分
   - 确认人声声部（S/A/T/B）已完全清除
   - 确认开头部分未遗漏

**注意事项：**
- 不同乐谱的Y坐标范围不同，需先分析再确定
- 第一页布局常与其他页不同，必须单独处理
- 切割范围宁可稍大勿小，避免遗漏内容
- 输出文件命名规范：`{曲名}_钢琴部分_固定范围切割.pdf`

#### 2.2 其他预处理方案

- 动态范围切割：根据检测到的声部标识自动调整范围
- 遮罩清除：用白色矩形遮盖不需要的区域
- 内容擦除：直接删除指定区域的PDF内容

### 第三步：OMR 识别

#### 3.1 Audiveris OMR引擎

**当前使用方案：**
- 引擎：Audiveris（Java实现的传统OMR）
- 输入：预处理后的PDF或PNG图像
- 输出：MusicXML 4.0格式

**转换流程：**
1. PDF → PNG图像（300 DPI，使用PyMuPDF）
2. 逐页调用Audiveris进行OMR识别
3. 提取.mxl文件中的XML内容
4. 合并所有页面为完整MusicXML文件

**性能说明：**
- 单页识别时间：约5-6秒
- 31页总耗时：约3分钟
- Audiveris为CPU引擎，不支持GPU加速
- 优化方向：批量模式（一次传入多张图片）

**合并逻辑要点：**
- Audiveris生成的.mxl是zip压缩格式，需解压提取XML
- 各页面XML无命名空间，直接用标签名查找
- 所有页面part的id相同（通常为"P1"），需合并measure到同一part
- 使用lxml进行XML解析和合并

**输出验证：**
- 检查Part数量（钢琴谱应为1-2个）
- 检查总小节数是否合理
- 检查文件大小（正常应>100KB）

## 文件操作安全铁律（宪法级 · 强制执行）

> **背景**：2026-07-26 BASS 训练 checkpoint（`horfen_bass_best.pt`）及 232 首训练数据在归档操作中丢失，根因是归档后未闭环验证。此后所有文件移动/复制/删除操作必须遵守本规则。

### 核心原则

**任何文件操作，必须形成"操作→验证→确认"闭环。禁止在验证通过前声称操作完成。**

### 操作前：三查

每次文件移动/复制/删除/归档前，必须执行：

1. **查源路径**：`ls` 确认源文件/目录存在，记录文件数量和总大小
2. **查目标路径**：`ls` 确认目标父目录存在，不存在则先创建
3. **查冲突**：若目标已存在同名文件，必须先报告用户，不得静默覆盖

### 操作后：三验

每次文件操作完成后，必须执行：

1. **验存在**：`ls` 目标路径，确认文件/目录已写入
2. **验大小**：对比源和目标文件大小，偏差>1% 必须报告
3. **验可用**：对于 `.pt` checkpoint、`.mid` 模型文件、训练数据等关键文件，必须尝试加载验证（`torch.load` 或等效操作），确认无损坏

### 删除操作：双保险

1. **禁止直接删除**：关键数据（checkpoint、训练数据、模型权重、用户乐谱）禁止直接 `rm` / `del`
2. **先移后删**：先 `mv` 到 `temp/归档/` 或回收站，确认无误后再清理
3. **源路径保留**：移动操作后，源路径保留副本至少到本次 session 结束，确认目标可用后再手动清理

### 大规模数据整理：先计划后执行

涉及 ≥10 个文件或 ≥1GB 数据的整理操作，必须：

1. **先出计划**：列出所有源路径→目标路径映射，预估数据量
2. **用户确认**：展示计划，等用户说"OK"后再执行
3. **分批执行**：每批 ≤50 个文件，每批执行后立即验证
4. **全程记录**：操作日志写入 `.trae/logs/file_operations.log`

### 违规后果

违反本规则导致数据丢失，视为 **P0 级事故**，必须在同一 session 内：
1. 立即停止当前操作
2. 向用户如实报告丢失内容和可能原因
3. 提出恢复方案（从备份恢复 / 重新生成 / 重新训练）

## 沙箱测试隔离规则（铁律）

### 核心原则

**沙箱测试与生产环境完全隔离。** 压力测试、技术验证、实验性修改不得影响原有的生产配置和代码。原有方案在简单乐谱场景下已充分胜任，沙箱测试中的调试方向和参数调整未必正确，需验证通过后才能补充到原有方案。

### 隔离规则

1. **测试脚本隔离**：所有一次性测试脚本放在 `temp/scripts/`，不得混入生产目录（`score_converter/`、`web/` 等）
2. **测试输出隔离**：所有测试输出放在 `temp/test_output/`，每个测试独立子目录
3. **生产配置不可改**：压力测试期间，禁止修改 `INSTRUMENT_DISPATCH`、`INSTRUMENT_CONFIGS`、`ScoringEngine` 等生产配置，只允许读取
4. **新方案独立文件**：任何新方案（如合奏转谱、鼓识别、Demucs分离）必须创建独立文件，通过 `instrument` 参数的新分支值驱动，不得修改原有单乐器路径
5. **调试参数不回写**：测试中为适配特定场景调的参数（容差、阈值、灵敏度），不得回写到生产配置，需在测试报告中记录
6. **临时依赖不污染**：测试中安装的临时依赖包，确认前不加入 `requirements.txt`
7. **测试后清理**：测试完成后，删除不再需要的临时文件、中间产物、`__pycache__/`，仅保留分析报告和可复测工具脚本

### 新旧方案并存架构

```
原有方案（简单乐谱 → 充分胜任，不可改动）
├── piano_transcribe.py     → INSTRUMENT_DISPATCH = [piano, guitar, violin, flute]
├── piano_pdf_to_musicxml.py → 单乐器PDF转谱（Audiveris）
├── ScoringEngine           → INSTRUMENT_CONFIGS（4种乐器配置）
└── collaborative_service.py → 单乐器协同模式

新方案（复杂乐谱 → 沙箱验证中，独立文件）
├── audio_separator.py      → instrument="ensemble" 分支（Demucs多声部）
├── drum_transcriber.py     → 鼓识别（信号处理方案）
├── ensemble_pdf_to_musicxml.py → 合奏PDF转谱（标签分割方案）
└── 需验证通过后才能并入主流程
```

### 合并条件

- 新方案必须在沙箱测试中达到最低质量标准
- 新方案不得破坏原有单乐器路径的任何功能
- 合并前需在 `analysis_core.py` 中增加对应的 `INSTRUMENT_DISPATCH` 条目
- 合并后需清理所有沙箱临时文件

## 模型训练 KL 验证规则（强制执行 · 宪法级）

> **背景**：Horfen 系列模型在生产环境运行。任何对生产模型的再训练/微调/联合训练都存在**灾难性遗忘**风险——新数据可能覆盖已有知识，导致旧风格/旧乐器识别能力退化。KL 散度验证是防止遗忘的**最后一道闸门**。

### 核心原则

**任何对生产模型的再训练/微调/联合训练，必须经过 KL 散度验证。KL 验证未通过，不得替换生产模型。**

### 训练流程铁律（五步闭环）

| # | 步骤 | 操作 | 闸门 |
|---|------|------|------|
| 1 | **Copy 隔离** | 从生产 checkpoint copy 到训练目录，生产文件只读不写 | 生产模型零修改 |
| 2 | **KL 基线采集** | 训练前，用生产模型在验证集上推理，保存每类输出的概率分布 P_old | 建立遗忘参照系 |
| 3 | **每轮 KL 监控** | 训练每轮结束后，用当前模型在同一验证集上推理，计算 KL(P_old ‖ P_new) | 实时检测分布偏移 |
| 4 | **KL 告警/阻断** | KL > 0.1 → 🟠 遗忘告警；KL > 0.2 → 🔴 阻断训练 | 防止不可逆退化 |
| 5 | **验证通过再替换** | KL 达标 + 各项指标达标 → 备份旧模型 → 替换生产模型 | 闭环可回退 |

### KL 散度计算规范

```python
def compute_kl_divergence(p_old: np.ndarray, p_new: np.ndarray, epsilon: float = 1e-10) -> float:
    """
    计算 KL(P_old || P_new) 逐类平均值
    
    Args:
        p_old: 生产模型输出概率 (N_samples, N_classes)，值域 [0, 1]
        p_new: 训练中模型输出概率 (N_samples, N_classes)，值域 [0, 1]
    
    Returns:
        mean KL divergence across all classes
    """
    p_old = np.clip(p_old, epsilon, 1 - epsilon)
    p_new = np.clip(p_new, epsilon, 1 - epsilon)
    kl_per_class = p_old * np.log(p_old / p_new) + (1 - p_old) * np.log((1 - p_old) / (1 - p_new))
    return float(np.mean(kl_per_class))
```

### 阈值定义

| 阈值 | 级别 | 含义 | 处置 |
|------|------|------|------|
| KL ≤ 0.05 | 🟢 正常 | 分布几乎无偏移，遗忘风险极低 | 继续训练 |
| 0.05 < KL ≤ 0.10 | 🟡 注意 | 轻微偏移，可能在正常泛化范围内 | 记录日志，观察趋势 |
| 0.10 < KL ≤ 0.20 | 🟠 告警 | 显著偏移，旧知识正在被覆盖 | 暂停训练，检查每类偏移，考虑调整学习率或增加旧数据比例 |
| KL > 0.20 | 🔴 阻断 | 严重遗忘，继续训练将不可逆退化 | 立即停止训练，回退到上一个 KL < 0.10 的 checkpoint |

### 验证集选择

- **必须覆盖旧风格**：KL 验证集必须包含原训练风格的样本（如 HorfenDrums 的 rock 数据）
- **不得用训练集**：KL 验证集必须与当前训练集不重叠，否则 KL 值失真
- **固定不变**：KL 验证集在整个训练过程中保持不变，确保可比性

### 按风格细粒度 KL

对于多风格联合训练，必须**按风格分别计算 KL**：

```python
kl_by_style = {
    "rock": compute_kl(p_old_rock, p_new_rock),
    "jazz": compute_kl(p_old_jazz, p_new_jazz),
    "fusion_jazz": compute_kl(p_old_fusion, p_new_fusion),
    "metal": compute_kl(p_old_metal, p_new_metal),
}
# 验收：所有风格 KL ≤ 0.10，且原风格（rock）KL ≤ 0.05
```

### 替换生产模型的前置条件

**必须同时满足以下所有条件，才能替换生产模型：**

1. 🔴 所有风格 KL ≤ 0.10，原风格 KL ≤ 0.05
2. 🔴 每种风格 F1 ≥ 0.70（或约定的最低标准）
3. 🔴 原风格 F1 下降 ≤ 0.02（不遗忘）
4. 🟡 总体 mean F1 提升 ≥ 0.02（有收益）
5. **操作安全**：备份旧模型后再替换（遵守文件操作安全铁律）

### 违规后果

- 跳过 KL 验证直接替换生产模型 → 🔴 阻断级违规，视为对生产环境的未授权变更
- KL 告警后继续训练且未记录 → 🟠 设计风险，后续验收时需补充说明

## 生成物只读规则（强制执行）

> 参考 `agent_constitution.md` §设计规则 §5

**核心原则：生成物只读不手改。** 发现 `DO NOT EDIT`、生成目录、schema/codegen 输出、bundle artifact 或迁移生成物时，必须找到源文件和生成命令；需要变更时改源并重新生成。

**常见生成物识别：**
- 文件头部含 `DO NOT EDIT` / `AUTO-GENERATED` / `generated by` 等标记
- `dist/`、`build/`、`node_modules/` 等构建产物目录
- `*.generated.*`、`*.codegen.*` 等命名模式
- 锁文件（`package-lock.json`、`yarn.lock` 等）

**违规示例：**
```python
# ❌ 错误：手改生成文件
# 文件头部有 "# DO NOT EDIT — generated by codegen.py"
# 但 agent 直接修改了文件内容
```

**正确做法：**
1. 找到生成该文件的源文件（如 `codegen.py`）
2. 修改源文件
3. 重新运行生成命令
4. 检查生成输出是否达到预期

## 外部输入资源上界规则（强制执行）

> 参考 `agent_constitution.md` §设计规则 §6

**核心原则：所有外部输入、队列、缓存、请求体、响应体、文件大小、重试、超时和后台 worker 都应有上界、背压、释放或降级策略；禁止无界增长和永久常驻的隐性运行面。**

**必须设上界的场景：**

| 场景 | 上界示例 | 无上界的风险 |
|------|---------|------------|
| 文件上传大小 | 50MB（FastAPI 请求体限制） | 内存耗尽 |
| 子进程运行时间 | 1小时（`_run_with_liveness_monitor`） | 永久挂起 |
| 轮询重试次数 | 3次（`task.js` maxRetries） | 无限重试 |
| 缓存条目数 | LRU 上限 | 内存无限增长 |
| 并发任务数 | 线程池/进程池大小 | 系统资源耗尽 |
| 日志文件大小 | 滚动日志 + 保留天数 | 磁盘占满 |
| API 速率限制 | 每秒/每用户限制 | 被上游封禁 |
| 队列积压 | 最大长度 + 拒绝策略 | 内存溢出 |

**执行原则：**
- 新增任何外部交互功能时，必须同时设计上界和超限策略
- 发现现有代码中无上界的资源使用时，报告为 🟠 设计风险
